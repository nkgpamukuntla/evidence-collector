The system

What you are hosting

The collector measures a public entity's actual security controls (a county, a court) against versioned control sets. It reads those controls through read-only credentials the entity grants. It stores raw responses, turns them into observations, and evaluates the observations into a per-entity evidence record that the entity owns and releases. Microsoft Graph is the first source; other vendors (EDR, backup, training) follow as separate adapters.

It has three parts to host: a worker that calls the sources and writes sealed raw bundles to S3; an evaluator with no network access that turns stored data into results; and a PostgreSQL 16 database holding the ledger, the observations and the evaluations. A deadman alarm pages when collection stops.

2 · Constraints

Rules the design must keep

These are settled. Each one is either enforced by a test or recorded as a decision in the repository. If one blocks a design you prefer, raise it with Tim, with evidence. Please don't work around it.

  1. R1
    A new AWS account, separate from PRISM.No code or infrastructure is carried over from the predecessor platform. Stack choices only.
  2. R2
    Everything through Terraform. Nothing configured by hand.The Terraform files are the reviewed record of what exists. A console change is invisible to that review.
  3. R3
    No private key on disk, in a vault or in a file.The Microsoft credential is a non-exportable KMS RSA-2048 key. The token request is signed with kms:Sign. Every county will trust that key, so it never exists outside KMS.
  4. R4
    Each key policy is the only authority over its key.No statement delegates to the account root. Key administrators can manage keys but cannot use them. Nobody gets kms:CreateGrant, because a grant lets its creator give themselves Decrypt without the policy changing. This affects RDS (section 5).
  5. R5
    Source credentials never pass through Terraform.Terraform state stores every attribute, secret values included. Onboarding writes credentials into Secrets Manager under ec/<env>/source/.
  6. R6
    The evaluator has no internet.Its only egress is S3 (the raw bucket), KMS and Postgres, enforced by its security group and endpoint policies. The worker, which calls Microsoft, gets its own subnets and route table.
  7. R7
    Read-only access to every measured entity, granted by the entity.Microsoft access is a multi-tenant Entra app: application read permissions, certificate authentication, verified publisher. Never GDAP, never CSP admin rights, never Lighthouse. D-Biz's CSP relationship through TD SYNNEX may be used to provision test tenants, never to read one.
  8. R8
    Compute runs on Graviton.ECS on Fargate, runtime_platform ARM64, images built for linux/arm64 only (decided on cost). CI tests on x86 today, so the ARM image needs a test run of its own.
  9. R9
    PostgreSQL 16.Pinned to 16.15 by image digest locally and in CI. Every database behavior the migrations rely on was verified on 16. Moving the major version is a decision with a full test run attached.
  10. R10
    Do not deploy the deadman alarm before the collector's process entry point exists.The alarm fires when the heartbeat metric stops arriving. Until the service that publishes the heartbeat is running, it would page continuously, and a deadman that always pages gets muted.
  11. R11
    Never describe the database as tenant isolation.Row-level security keys on context the client sets, so it separates code paths, not principals. What holds against a compromised component is the grants.
3 · Existing code

Terraform already written

Terraform 1.16.3 and AWS provider 6.65.0, both pinned. bash tools/terraform.sh check runs fmt, validate and the tftest suites against a mocked provider with no AWS call. CI runs the same script. A Python test holds what a mock cannot show, such as the absence of any route off the VPC.

FileWhat it creates
kms.tfFour kinds of key, one job each (below).
s3.tfThe raw-bundle bucket: Object Lock in governance mode for 90 days, versioned, never public, and a policy tying each tenant's prefix to that tenant's key.
iam.tfThree roles. worker writes bundles and cannot read them. evaluator reads them and nothing else. terminator is for humans with MFA, and is the only thing that can reach inside a lock.
liveness.tfThe in-account half of the deadman: an SNS topic only CloudWatch may publish to, and an alarm that fires when the heartbeat stops (missing data counts as breaching).
network.tfThe evaluator's fence: subnets with no route off the VPC, an S3 endpoint that admits the raw bucket only, and a security group whose only egress is S3, KMS and Postgres.
KeyTypeWho may use it, and for what
raw[tenant]Symmetric, yearly rotationWorker seals bundles through S3; evaluator opens them through S3; both bound to that tenant's prefix. Terminator schedules deletion.
signingRSA-2048, sign/verifyWorker signs with RS256 only: the Microsoft client assertion.
fingerprintHMAC-256Worker generates the credential fingerprint recorded on every exchange.
secretsSymmetric, yearly rotationWorker decrypts source credentials under ec/<env>/source/. Onboarding, if named, writes them.

Decisions already made in that code

  • Keys are per tenant. Terminating a tenant means scheduling its key for deletion. After the 30-day window, every copy of its bundles is unreadable.
  • At most 36 tenants per deployment. The bucket policy carries about 510 bytes per tenant and AWS caps it at 20 KB; 40 tenants measured at 21,014 bytes. Past 36, the per-tenant rule moves to per-tenant access points, which is a design change.
  • S3 Bucket Keys are off, so each object's encryption context binds its key to its own tenant's prefix. Cost: one KMS request per bundle.
  • No multipart uploads, which would need kms:Decrypt for the worker. One PUT takes up to 5 GB.
  • Governance mode, not compliance mode, because deletion on termination is required. The terminator role can bypass the lock; nothing else can.
4 · Sequence

Hosting, in order

  1. Create the account and pick the region.

    The cost estimate assumed us-east-1; the region is not decided. Turn on CloudTrail. The key design relies on it to make any key-policy change visible, and it is not in infra/ yet.

  2. Decide where Terraform state lives and add the backend.

    No backend is configured. State must never hold a secret, which is why R5 exists.

  3. Create the human principals.

    Key administrators: the principal that runs terraform apply must be one of them, or KMS refuses every key policy as a lockout. Terminator principals: humans only, with MFA. Secret writers for onboarding: may be empty at first.

  4. Write a .tfvars locally and never commit it.

    It is in .gitignore. The variables are below.

  5. Apply to a dev environment first.

    Every resource name carries the environment (ec-dev-…), so dev and prod can share an account or live in separate ones. That choice is open (section 9).

How the live run is driven

uv run python tools/tenant_matrix.py run \
  --tenant <tenant-uuid> --profile <profile> --generation <n> \
  --client-id <app-client-id> \
  --kms-key-id <signing-key-id> --cert <public-cert.pem>

It signs through the KMS key, never a local key. The predicted answers (54 cells, none observed yet) are in source-catalogs/microsoft/graph-matrix.json; an answer the prediction did not allow fails the run rather than being fitted.

Later: the canary tenant

A tenant whose controls are held in known states and flipped on a schedule. Each collection cycle must detect the flip, and a cycle whose canary did not report cannot be published. The six-month go/no-go gate (March 2027) needs it running for eight consecutive weeks with no silent miss, so it is worth planning alongside the other three.

8 · Root of trust

The app registration and its home tenant

Every county that consents trusts the application id, not a particular key. A certificate added to the registration's credentials in our home tenant is honored by every consenting tenant, and a county cannot see that list. So the home tenant is the most sensitive thing we run. Before the first county consents:

  • Two named people hold the roles and ownership that can add a credential (Application Administrator, Cloud Application Administrator, owners of the registration), under PIM with phishing-resistant MFA. The registration has no other owner.
  • The default app-management policy blocks password secrets. It cannot block a second certificate; Microsoft says so.
  • Any change to the registration's certificate list raises an alert.
  • Publisher verification is complete, through the Microsoft partner account.
  • Each county's record will carry the thumbprints of the certificates we hold, so a mismatch is at least detectable afterwards.

The certificate

A self-signed X.509 certificate whose own signature is a kms:Sign by the signing key, so the private key never leaves KMS. The tool that makes it is not written yet; it is built once the account exists. It also needs to issue a short-lived certificate, so we can observe what Microsoft returns when one expires. Renewal: a successor is uploaded before the incumbent expires (the credential list holds several), and the collector will refuse to run within 14 days of expiry.

Blocked on a decision

Which tenant hosts the registration is open (D7). Its publisher name appears on every county's consent screen, and the product may not carry D-Biz's name to the client. Please don't create the production registration until Tim settles this. A registration in a D-Biz test tenant for the matrix run is fine.
